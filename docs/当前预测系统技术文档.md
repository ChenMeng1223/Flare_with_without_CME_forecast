## 1. 一句话概览

当前系统不是单纯的“整张图分类模型”，而是一个级联式预测管线：

```text
原始事件表 / 多波段观测数据
  -> 下载与预处理
  -> HDF5 事件级数据集
  -> 滑动窗口 window
  -> YOLO11 生成活动区 proposal
  -> 多模态时序 Stage2 模型对 proposal 做分类 / bbox refine / 可选时间预测
  -> 后处理阈值过滤、NMS、merge
  -> JSON / CSV / 可视化 / 指标评估
```

当前最重要的输出类别约定：

| 类别 | 含义 | 是否作为最终事件输出 |
|---|---|---|
| `0` | no-event / padding / 负槽位 | 否，只作为内部训练和过滤类别 |
| `1` | eruptive / CME-related | 是 |
| `2` | confined | 是 |

当前最容易混淆的三个层级：

| 层级 | 含义 | 数量 |
|---|---|---|
| `event` | 一个太阳事件序列 | 不定 |
| `window` | 从 event 中切出来的固定长度时序片段 | 一个 event 可有多个 |
| `slot / activity` | 一个 window 内固定长度的候选位置 | 当前 5 或 15，取决于配置 |
| `detection` | 后处理后最终保留下来的预测框 | 不定 |

### 2.3 Stage 2：多模态时序模型

Stage2 模型仍然使用 `models/multimodal_transformer.py::MultimodalTransformer`。它可以：

1. 编码多模态时序图像。
2. 如果输入里有 `proposal_boxes`，则优先使用外部 YOLO proposal。
3. 如果没有外部 proposal，则使用内部 `ProposalDecoder` 作为 baseline。
4. 对每个 proposal 抽取 local ROI 和 context ROI。
5. 对 ROI 时序做 Transformer 编码。
6. 输出每个 slot 的类别、事件概率、精修 bbox、可选时间预测。

当前 Stage2 checkpoint 示例：

```text
outputs/checkpoints_stage2_yolo11_5modal/solar_flare_cme_model_epoch_0114.pth
```

当前 5 模态 Stage2 配置：

```text
configs/data_config_stage2_yolo11_5modal_256.yaml
configs/training_config_stage2_yolo11_5modal.yaml
configs/inference_config_stage2_yolo11_5modal_256.yaml
```

### 2.4 Stage 3：后处理与评估

后处理入口：

```text
inference/post_processing.py::PostProcessor.process()
```

主要步骤：

1. 压缩 batch 维。
2. 根据 class probability 得到 slot 级 `final_classes`。
3. 处理时间预测，把 day 单位转为 hour 单位。
4. 处理 event probability。
5. 处理 bbox，过滤无效框和低置信度 slot。
6. 去掉 `class_id == 0` 的 no-event slot。
7. NMS。
8. 高 IoU detection merge。
9. 输出最终 detections。

### 5.3 slot 与 detection 的区别

训练时：

```text
GT slot k <-> prediction slot k
```

后续 trainer 里已经引入 Hungarian supervision 辅助目标构建，但仍要注意：数据集层是固定 slot，后处理层是非固定 detection。

推理时：

```text
原始 15 个 slot
  -> class/event/proposal 阈值过滤
  -> 去掉 class 0
  -> NMS
  -> merge
  -> N 个 final detection
```

因此：

| 字段 | 含义 |
|---|---|
| `slot_id` | 原始模型输出槽位编号 |
| `detection_idx` | 后处理保留下来的第几个 detection |
| `kept_bbox_slot_indices` | final detection 追溯到哪些原始 slot |

## 6. 模型架构细节

核心文件：

```text
models/multimodal_transformer.py
```

### 6.1 总体结构

```text
inputs: {modality: (B,T,C,H,W)}
  -> SpatialModalityEncoder × N
  -> MultimodalSpatiotemporalFusion
  -> fused_maps / temporal_features / global_feature
  -> ProposalDecoder 内部 proposal
  -> 如果 inputs 有 proposal_boxes，则替换为外部 proposal
  -> stage2_boxes = mix(predicted / gt / jittered_gt)
  -> context_boxes = expand(stage2_boxes, context_scale)
  -> grid_sample 抽取 local/context ROI
  -> RoiTemporalEncoder
  -> StageTwoPredictor
  -> class_logits / class_probs / event_prob / bbox_pred / time_pred
```

### 6.2 `SpatialModalityEncoder`

输入：

```text
(B,T,C,H,W) 或 (B,T,H,W)
```

结构：

```text
Conv2d -> BatchNorm2d -> ReLU -> MaxPool2d(2)
Conv2d -> BatchNorm2d -> ReLU -> MaxPool2d(2)
Dropout2d
```

输出：

```text
(B,T,hidden_dim,H/4,W/4)
```

当输入为 256×256 时，输出空间尺寸约为 64×64。

### 6.3 `MultimodalSpatiotemporalFusion`

步骤：

1. 对每个模态特征图做空间平均池化，得到 `(B,T,D)`。
2. 如果多模态，使用 cross-modal attention，让当前模态 query 关注其他模态 key/value。
3. 多模态增强结果求平均得到 `fused_sequence`。
4. 多模态空间特征图直接求平均得到 `fused_maps`。
5. `fused_sequence` 进入 temporal Transformer。
6. temporal features 加回 fused maps。
7. 对时间维取平均得到 `global_feature`。

输出：

| 字段 | 形状 | 含义 |
|---|---|---|
| `fused_maps` | `(B,T,D,H',W')` | 融合后的时空特征图 |
| `temporal_features` | `(B,T,D)` | 时序编码结果 |
| `global_feature` | `(B,D)` | 全局序列表征 |

### 6.4 `ProposalDecoder`

内部 baseline proposal 生成器。它把 `fused_maps` 展平成时空 token：

```text
(B,T,D,H',W') -> (B,T*H'*W',D)
```

再使用 `max_activities` 个 learnable query 读出固定数量 proposal。

输出：

| 字段 | 形状 | 含义 |
|---|---|---|
| `proposal_boxes` | `(B,A,4)` | 内部候选框 |
| `proposal_scores` | `(B,A,1)` | 内部 objectness |
| `proposal_features` | `(B,A,D)` | proposal 特征 |
| `external_proposals` | `False` | 标记来源 |

### 6.5 外部 YOLO proposal 接入

`MultimodalTransformer.forward()` 中：

```python
if "proposal_boxes" in inputs and inputs["proposal_boxes"] is not None:
    proposal_outputs = self._resolve_external_proposals(...)
```

外部 proposal 要求：

```text
proposal_boxes:  (B,A,4), normalized xyxy
proposal_scores: (B,A) 或 (B,A,1)
```

外部 proposal 接入后：

| 字段 | 处理方式 |
|---|---|
| `proposal_boxes` | 直接来自输入 |
| `proposal_scores` | 来自输入，不存在则补 1 |
| `proposal_features` | 暂时用 `global_feature` 复制到每个 slot |
| `external_proposals` | `True` |

这意味着当前 Stage2 主要依赖 bbox 几何位置 + 多模态 ROI 特征 + proposal score，尚未使用 YOLO backbone embedding。

### 6.6 ROI 抽取

模型用 `grid_sample` 做归一化 bbox ROI 采样，不依赖 torchvision ROIAlign。

输入：

```text
fused_maps: (B,T,D,H',W')
boxes:      (B,A,4)
```

输出：

```text
local_roi_maps:   (B,A,T,D,roi_size,roi_size)
context_roi_maps: (B,A,T,D,roi_size,roi_size)
```

默认 `roi_size = 4`。

context box 通过 `context_scale=2.0` 从 proposal 扩张得到。

### 6.7 `RoiTemporalEncoder`

每个 ROI 每帧先做自适应平均池化，然后对时间序列做一层 TransformerEncoder。

输出：

| 字段 | 形状 | 含义 |
|---|---|---|
| `sequence` | `(B,A,T,D)` | ROI 时序特征 |
| `pooled_feature` | `(B,A,D)` | slot 级 ROI 特征 |

### 6.8 `StageTwoPredictor`

融合特征：

```text
local_feature
context_feature
proposal_feature
global_feature
proposal_scores
```

拼接维度：

```text
hidden_dim * 4 + 1
```

输出：

| 字段 | 形状 | 含义 |
|---|---|---|
| `class_logits` | `(B,A,3)` | 三类 logits |
| `class_probs` | `(B,A,3)` | softmax 概率 |
| `event_prob` | `(B,A,1)` | event/objectness logit |
| `event_gate` | `(B,A,1)` | sigmoid(event_prob) |
| `bbox_pred` | `(B,A,4)` | refined bbox |
| `time_pred` | `(B,A,3)` | 时间预测，时间头关闭时为 0 |
| `slot_features` | `(B,A,D)` | slot 表征 |

bbox refine 使用：

```text
proposal_center + tanh(delta_center) * proposal_size * refine_center_scale
proposal_size * exp(tanh(delta_log_size) * refine_size_log_scale)
```

## 7. 损失函数与训练逻辑

核心文件：

```text
training/trainer.py
```

核心类：

```text
SolarFlareTrainer
```

### 7.1 优化器与调度器

支持：

| 类型 | 说明 |
|---|---|
| `adam` | 标准 Adam |
| `adamw` | 当前默认 |
| `sgd` | 可选 |
| `cosine` | 余弦调度 |
| `step` | step 调度 |
| `plateau` | 当前默认 ReduceLROnPlateau |

### 7.2 损失项

| 损失项 | 实现 | 作用 |
|---|---|---|
| `classification` | CrossEntropyLoss | 正样本 slot 上做 1/2 分类 |
| `proposal_score` | BCEWithLogitsLoss | slot 是否有事件 |
| `proposal_bbox` | L1 + GIoU | 第一阶段 proposal 对齐 GT |
| `bbox` | L1 + GIoU | refined bbox 对齐 GT |
| `time` | SmoothL1Loss | 时间预测，当前 5modal 权重为 0 |
| `event_prob` | BCEWithLogitsLoss | event probability |
| `suppression` | L1Loss | 负 slot 抑制 |
| `physics` | 物理约束模块 | 当前可开关 |

### 7.3 分类监督

分类不是简单的 0/1/2 三类等权训练。当前核心逻辑是：

```text
正 slot: label in {1,2}
负 slot / padding: 不参与 eruptive/confined 分类损失
```

`class_logits[..., 1:]` 参与 1/2 二分类损失。`class 0` 主要通过 proposal score、event prob、suppression 和后处理规则起作用。

### 7.4 bbox 监督

当前 trainer 中有 Hungarian supervision 相关逻辑：

```text
_build_hungarian_supervision_targets
_build_region_hungarian_supervision_targets
```

这用于缓解固定 slot 对齐的问题。但需要注意，Dataset 输出仍然是固定长度 slot，评估与导出时仍要区分 slot 和 final detection。

### 7.5 负槽位抑制

对没有真实事件的 slot，训练中会促使：

```text
bbox 尺寸更小
time duration 更短或接近 0
event_prob 更低
```

这是减少 no-event slot 产生虚假 detection 的关键机制。

### 7.6 验证指标

训练中综合指标：

```text
0.35 * F1
+0.25 * IoU
+0.20 * TSS
+0.10 * loss_term
+0.05 * cls_loss_term
+0.05 * rmse_term
```

其中当前 time head 常关闭或 time loss 权重为 0，因此 RMSE 项可能不敏感。

## 9. 评估方式

### 9.1 常规推理里的 slot 分类评估

`scripts/g_inference_pipeline.py` 中测试集指标主要按 activity slot 聚合：

```text
GT activity slot <-> prediction slot/final class
```

它不是严格事件级，也不是完整 detection mAP。

### 9.2 级联评估里的 detection 指标

`scripts/r_cascade_yolo11_stage2_inference.py` 会：

1. 对每个 window 生成 YOLO proposal。
2. 运行 Stage2。
3. 后处理得到 predicted boxes。
4. 从 GT 中提取 unique region boxes。
5. 用 IoU 贪心匹配。
6. 统计 TP/FP/FN、precision、recall、F1。
7. 在 IoU 匹配成功的 detection 上统计分类 accuracy/F1。

输出指标位置：

```text
outputs/cascade_yolo11_stage2_5modal_test/cascade_metrics.json
```

### 9.3 建议的评估口径

当前系统里，`pred_cls < 0` 只能说明“这个 slot 最终没有有效预测”，不能直接等价成 FN。  
真正要看的是这个 slot 在 GT 里有没有活动对象。

#### 9.3.1 符号定义

| 符号 | 含义 |
|---|---|
| `gt_activity_mask=True` | 真实存在活动对象的 slot |
| `gt_activity_mask=False` | 真实不存在活动对象的 slot / padding slot |
| `gt_label>0` | 该 slot 是正类 |
| `pred_cls>=0` | 模型给出了有效类别 |
| `pred_cls<0` | 模型未给出有效类别，等价于空预测 |

#### 9.3.2 二分类最清楚的定义

如果把问题先压成“这个 slot 有没有活动对象”，推荐这样记：

| 情况 | GT | 预测 | 记作 |
|---|---|---|---|
| 真实有活动，模型也给出有效预测 | `gt_activity_mask=True` 且 `pred_cls>=0` | 预测存在 | `TP` |
| 真实没活动，模型也没给出预测 | `gt_activity_mask=False` 且 `pred_cls<0` | 预测不存在 | `TN` |
| 真实没活动，但模型给出了预测 | `gt_activity_mask=False` 且 `pred_cls>=0` | 误报 | `FP` |
| 真实有活动，但模型没给出预测 | `gt_activity_mask=True` 且 `pred_cls<0` | 漏报 | `FN` |

所以，“没输出”本身不是 FN。  
只有当 GT 里本来有活动时，没输出才是 FN。

#### 9.3.3 分类视角下的细分

当 slot 已经确定是活动 slot 后，还可以继续看类别是否对：

| 情况 | 解释 |
|---|---|
| `pred_cls == gt_label` | 分类正确 |
| `pred_cls < 0` 且 `gt_activity_mask=True` | 活动 slot 被漏掉 |
| `pred_cls != gt_label` 且 `pred_cls>=0` | 类别错误 |
| `gt_activity_mask=False` 且 `pred_cls>=0` | 背景误报 |
| `gt_activity_mask=False` 且 `pred_cls<0` | 背景正确空预测 |

#### 9.3.4 两个 precision 的区别

| 指标 | 统计范围 | 主要含义 | 是否惩罚背景误报 |
|---|---|---|---|
| `classification_activity_only_precision` | 只看 `gt_activity_mask=True` 的 slot | 真活动上的分类是否准 | 否 |
| `classification_all_slots_precision` | 所有 slot 都算 | 整体是否乱报 | 是 |

#### 9.3.5 当前代码里容易误解的地方

1. `pred_cls < 0` 不等于“这个位置一定是 FN”
2. 对背景 slot 来说，`pred_cls < 0` 应该算 TN
3. 如果某段统计把 `pred_cls < 0` 直接跳过，会让 precision / recall 偏乐观
4. 训练器里的二分类指标，本质上是 slot 级统计，不是单纯框级统计

#### 9.3.6 建议最终同时报告的指标

建议至少同时保留三组：

| 组别 | 指标 |
|---|---|
| 活动槽位分类 | `classification_activity_only_precision / recall / f1` |
| 全槽位分类 | `classification_all_slots_precision / recall / f1` |
| 检测层面 | `region_iou_metrics.precision / recall / f1` |

这样就能分清三件事：

1. 真活动上分类是否准确
2. 背景上是否乱报
3. 最终框的位置是否对齐

#### 9.3.7 当正类分别是爆发耀斑或束缚耀斑时的 T P / T N / F P / F N

如果把三分类里的某一类单独拿出来当“正类”，另一类正类和背景一起都算“负类”，就是 one-vs-rest 的定义。

##### A. 以“爆发耀斑 / eruptive”作为正类

设：

- 正类：`gt_label == 1`
- 负类：`gt_label == 0 or 2`

则：

| 情况 | GT | 预测 | 记作 |
|---|---|---|---|
| 真实爆发耀斑，预测为爆发耀斑 | `gt_label=1` | `pred_cls=1` | `TP` |
| 真实不是爆发耀斑，预测也不是爆发耀斑 | `gt_label!=1` | `pred_cls!=1` | `TN` |
| 真实不是爆发耀斑，却预测成爆发耀斑 | `gt_label!=1` | `pred_cls=1` | `FP` |
| 真实爆发耀斑，却没预测成爆发耀斑 | `gt_label=1` | `pred_cls!=1` 或 `pred_cls<0` | `FN` |

这里的“不是爆发耀斑”包含两种情况：

1. 背景 / no-event
2. 束缚耀斑

所以这个 one-vs-rest 指标回答的是：

> 模型把爆发耀斑和“其他所有情况”区分开得怎么样？

##### B. 以“束缚耀斑 / confined”作为正类

设：

- 正类：`gt_label == 2`
- 负类：`gt_label == 0 or 1`

则：

| 情况 | GT | 预测 | 记作 |
|---|---|---|---|
| 真实束缚耀斑，预测为束缚耀斑 | `gt_label=2` | `pred_cls=2` | `TP` |
| 真实不是束缚耀斑，预测也不是束缚耀斑 | `gt_label!=2` | `pred_cls!=2` | `TN` |
| 真实不是束缚耀斑，却预测成束缚耀斑 | `gt_label!=2` | `pred_cls=2` | `FP` |
| 真实束缚耀斑，却没预测成束缚耀斑 | `gt_label=2` | `pred_cls!=2` 或 `pred_cls<0` | `FN` |

同样地，这里的“不是束缚耀斑”也包含：

1. 背景 / no-event
2. 爆发耀斑

##### C. 和当前代码里 `class_precision_12 / class_recall_12` 的关系

当前训练器里 `class_precision_12`、`class_recall_12` 实际上就是对正类 `1` 和 `2` 分别做 one-vs-rest 统计，然后再取平均。  
因此：

- `class_precision_12['1']` 可以理解为“爆发耀斑作为正类时的 precision”
- `class_precision_12['2']` 可以理解为“束缚耀斑作为正类时的 precision”

而 `class_tss_12['1']`、`class_tss_12['2']` 则分别是这两个正类的一对一 TSS。

##### D. 一句最实用的总结

当你说“爆发耀斑是不是被识别出来”，就是看：

- `TP`: 真爆发耀斑且判成爆发耀斑
- `FP`: 不是爆发耀斑却判成爆发耀斑
- `FN`: 真爆发耀斑却没判成爆发耀斑
- `TN`: 其他所有情况都没判成爆发耀斑

束缚耀斑完全同理，只是把正类从 `1` 换成 `2`。

## 11. 已知问题与待优化点

### 11.1 时间标签语义需要统一

旧文档中有 `start/end/duration`，当前模型 `_predict_time()` 中实际可输出 `start/peak/end`。同时 5modal 配置里：

```yaml
time_prediction: 0.0
prediction_heads.time.enabled: false
```

因此当前主线更应视为“分类 + bbox/refine + event probability”，时间预测暂时不是强监督主能力。

建议：

1. 明确 `time_features` 的唯一语义。
2. 将字段命名改为 `time_start/peak/end` 或 `time_start/end/duration`，不要混用。
3. 若重新启用时间头，同时打开 `prediction_heads.time.enabled` 和 `loss_weights.time_prediction`。

### 11.2 外部 YOLO proposal feature 过弱

当前 `_resolve_external_proposals()` 中：

```text
proposal_features = global_feature repeated
```

也就是说 Stage2 没有利用 YOLO detector 的中间 embedding，只利用了 bbox 和 score。

建议：

1. 从 YOLO backbone/neck 提取 ROI embedding。
2. 或新增几何特征编码：`x1,y1,x2,y2,w,h,area,score`。
3. 用 `ProposalFeatureProjector` 映射到 hidden_dim。

### 11.3 多模态融合仍较简单

当前空间特征图融合是多模态直接平均：

```text
fused_maps = mean(modality_maps)
```

这可能削弱某些模态的特殊贡献。

建议：

1. 使用可学习 modality gate。
2. 使用 per-pixel/per-region cross-modal attention。
3. 对缺失模态引入 mask，而不是简单 placeholder。

### 11.4 评估口径不完全统一

目前同时存在：

1. slot 级分类评估。
2. window 级 detection 评估。
3. event 级告警输出。

建议固定三张标准表：

| 表 | 一行代表 | 用途 |
|---|---|---|
| `window_summary` | 一个 window | 总览 |
| `slot_predictions` | 一个 window × 一个 slot | 调试训练/后处理 |
| `final_detections` | 一个 final detection | 业务输出/评估 |

`scripts/g_inference_pipeline.py` 已经开始生成 `predictions_slots_debug.csv`，这是正确方向。

### 11.5 YOLO 与 Stage2 分辨率存在两套尺寸

YOLO 当前常用 `imgsz=512`，Stage2 输入为 `256×256`。bbox 统一为归一化 xyxy，因此可以对齐，但可视化和原始 processed 图片尺寸必须小心。

建议：

1. 所有中间 bbox 都只存 normalized xyxy。
2. 绘图时再映射到当前底图像素。
3. 在输出 JSON 里记录 `bbox_coordinate_system = normalized_xyxy_top_left`。

### 11.6 后处理阈值偏召回模式

当前：

```yaml
min_event_probability: 0.00
min_proposal_score: 0.005
nms_threshold: 0.70
```

属于高召回、低过滤策略，容易带来 FP。

建议按目标分两套配置：

| 模式 | 目标 |
|---|---|
| recall mode | 找尽可能多候选，用于诊断 |
| precision mode | 减少误报，用于正式告警 |

### 11.7 `main.py` 聚合入口没有真正传递构造好的 args

`main.py` 中构造了 `train_args/predict_args/eval_args`，但实际调用 `train_main()` / `predict_main()` 没把这些 args 传进去。当前主要脚本都有自己的 argparse/direct config，所以 `main.py` 更像旧入口。

## 13. 建议的后续优化优先级

1. 先固定评估口径：正式区分 slot-level、detection-level、event-level。
2. 统一时间标签语义，并决定当前版本是否启用时间头。
3. 给外部 proposal 增加几何/YOLO embedding 特征，而不是只复制 global feature。
4. 建立 precision/recall 两套后处理配置。
5. 把 `main.py` 修成真正可用的统一入口，或明确废弃。
6. 把当前工作流配置写成一份 `configs/pipeline_current.yaml`，减少多处 direct config 分叉。
7. 为 `proposal_cache` 加版本元数据：YOLO 权重、conf、iou、frame_source、channel_modalities、image_source、生成时间。
8. 增加端到端 smoke test：加载 1 个 event，运行 YOLO proposal、Stage2、后处理、导出，验证输出字段完整。
